STRAPI PERMISSION MANAGER PRO — COMPLETE BUILD PLAN (WITH OWNER & CONTEXT MODEL)

OBJECTIVE:
Build a production-grade permission engine plugin that replaces:

* app-access config
* app-access-guard middleware

Supports:

* RBAC (roles)
* ABAC (conditions)
* Ownership (owners relation)
* Context-based access (app/domain + elevation)
* Field-level security
* Query-level enforcement

---

## PHASE 0 — CORE DESIGN PRINCIPLES

1. Replace headers with context:
   X-Rutba-App        → context.activeDomain
   X-Rutba-App-Admin  → context.isElevated

2. Ownership is NOT optional:

   * Must be enforced at query level
   * Must be part of policy system

3. Deny by default

4. Query filtering is mandatory

## PHASE 3 — CONTEXT RESOLVER (REPLACES HEADERS)

Build context per request:

context = {
user,
activeDomain,   // from header or session
isElevated,     // from header + role validation
teamIds,
roles
}

Rules:

* activeDomain required for app users
* isElevated only if user has admin role for domain

---

## PHASE 4 — PERMISSION ENGINE

API:
can(user, action, resource, entity, context)

Flow:

1. Resolve roles
2. Load policies
3. Evaluate conditions
4. Apply priority (deny > allow)

---

## PHASE 5 — CONDITION DSL (RELATION-BASED)

Examples:

Owner:
owners includes $user.id

Shared:
sharedWith includes $user.id

Manager:
owner.managerId = $user.id

Team:
teamId in $user.teamIds

Elevation:
isElevated = true

---

## PHASE 6 — QUERY FILTER BUILDER (CRITICAL)

Convert conditions → Strapi filters

Example:

{
"$or": [
{ "owners": { "$in": [user.id] } },
{ "sharedWith": { "$in": [user.id] } },
{ "owner": { "managerId": { "$eq": user.id } } }
]
}

Rules:

* Always push to DB
* Never rely only on JS filtering

---

## PHASE 7 — OWNER SCOPING (MANDATORY)

If resource has "owners" relation:

CREATE:
auto assign owner

READ:
filter by owners unless elevated

UPDATE/DELETE:
verify ownership unless elevated

If no owners relation:
elevated users get full access
